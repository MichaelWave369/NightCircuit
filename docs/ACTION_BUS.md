# NC-006 Action Bus Contract

NC-006 separates three facts that were previously easy to blur together:

1. **A command was well-formed.**
2. **The command was authorized.**
3. **The actor actually did something.**

Human interfaces are very good at pretending those are the same event. They are not.

## Action envelope

The Action Bus normalizes every proposal to:

```json
{
  "schema": "night-circuit/action/0.2",
  "action_id": "act-00000042",
  "sequence": 42,
  "source": "agent",
  "actor": "phi_bot",
  "action": "INSPECT",
  "payload": {},
  "request_id": "optional-caller-id",
  "replay_of": ""
}
```

### action_id

Generated by the Action Bus when omitted.

It correlates the decision receipt and effect receipt.

### request_id

Optional caller-supplied idempotency key.

The same source cannot reuse the same non-empty request ID in one session. A duplicate is rejected before actor execution.

### replay_of

Used when a replay entry submits an action derived from an earlier action.

## Actor registration

World actors register one execution callable:

```text
register_actor("hunter", hunter.execute_action)
register_actor("phi_bot", phi_bot.execute_action)
```

The Action Bus, not the input adapter, dispatches the authorized action.

That closes the old gap where authorization was recorded but actor execution happened only because every actor listened to a global signal.

## Decision receipt

A decision receipt answers:

> Was this proposal authorized?

Example:

```json
{
  "receipt_type": "decision",
  "action_id": "act-00000042",
  "accepted": true,
  "reason": "authorized",
  "actor": "phi_bot",
  "action": "PING"
}
```

## Effect receipt

An effect receipt answers:

> What did the actor report after execution was attempted?

Statuses:

- `applied`: actor changed intent/state or completed the requested operation
- `noop`: valid request, but nothing changed
- `refused`: actor received an authorized verb but current capability/state disallowed execution
- `failed`: execution infrastructure or result contract failed

Example:

```json
{
  "receipt_type": "effect",
  "action_id": "act-00000042",
  "status": "refused",
  "reason": "ability_unavailable_in_broken_form",
  "effect": {
    "form": "BROKEN"
  }
}
```

That distinction is intentionally visible with Φ-Bot PING in NC-006:

- Authority Gate: PING is a legitimate Φ-Bot verb.
- Broken Form: PING is not yet an installed ability.
- Decision: ACCEPTED.
- Effect: REFUSED.

This is much more informative than either pretending the command succeeded or rejecting the verb as if it can never exist.

## Replay tape

The Receipt Ledger can derive a replay-oriented tape from accepted decision receipts.

It includes:

- original action ID
- original sequence
- original source
- actor
- action
- payload

System boot actions are excluded.

A replay entry can be submitted back through the same Action Bus using source `replay`.

NC-006 does **not** claim deterministic simulation replay yet. It establishes the semantic input record required to qualify determinism later.

## Effect scope

An effect receipt reports the actor's immediate execution result.

For persistent intents:

- MOVE effect means movement intent changed.
- JUMP effect means jump buffering/release state changed.

It does not claim the Hunter physically moved a particular distance or successfully landed a jump.

Later simulation/event receipts can describe those downstream facts without corrupting the meaning of the command receipt.
